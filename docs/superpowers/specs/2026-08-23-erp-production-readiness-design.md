# ERP 生产化与业务补全设计

## 1. 背景与目标

当前项目已经具备订单、生产、员工、供应商、经销商、工资、任务、通知和设置等页面与 API，但线上部署仍不具备正式使用条件。审计确认的主要问题包括：线上 Supabase 缺少代码依赖的业务表；认证会话、验证码、OAuth state 和密码重置令牌保存在进程内存；RLS、Postgres Grants 和租户隔离不完整；订单与生产状态存在多套定义；部分页面仍使用占位数据；错误边界、输入验证、限流和测试覆盖不足。

本设计的目标是将项目逐步改造成可持续维护、可安全部署、具备完整业务闭环的多企业 ERP。改造必须保留现有 Supabase v2 组织/IAM 数据，不清空线上数据库，不以一次性大重写替换增量交付。

## 2. 已确认的决策

- `xiangzhi2022/erpv1` 是唯一开发源。
- `LOVEZHI163/erpv1` 作为自动同步镜像和 Netlify 部署源。
- 保留 Supabase v2 的组织/IAM 表与数据，在其上增量建设 ERP 业务层。
- Supabase Auth 成为唯一身份认证源，Next.js 使用 Cookie/SSR 会话。
- `enterprises` 是唯一企业主表，`enterprise_memberships` 是唯一成员关系来源。
- 所有 ERP 业务数据必须具有明确的 `enterprise_id`。
- 数据库迁移、RLS、约束和索引优先于业务页面补全。
- 订单、生产工单、工序任务、工资记录分别维护各自层级的状态，但状态定义必须来自唯一领域模块。
- 项目按独立阶段交付，每阶段必须可测试、可审查、可回滚。

## 3. 交付分解

### 阶段一：生产安全与数据底座

建立正式数据库迁移、Supabase Auth/SSR 会话、企业成员与权限上下文、RLS、统一 API 契约、限流、安全响应头、错误边界和部署门禁。该阶段完成前，不扩展新的业务功能。

### 阶段二：订单到结算的核心闭环

打通企业协作订单、拆单、生产工单、工序任务、进度上报、质检、返工、入库、发货、工资审批与结算。

### 阶段三：辅助模块与界面正规化

补齐员工、车间、供应商、经销商、任务、通知和系统设置，清除占位数据、乱码、重复页面和无效入口，统一 B2B ERP 交互。

### 阶段四：全面质量与发布体系

完善数据库、API、组件和端到端测试，建立性能、可观测性、预览环境和正式发布门禁。

每个阶段单独编写实施计划。阶段一是本设计批准后的首个实施范围。

## 4. 数据库与身份架构

### 4.1 身份与组织模型

```text
auth.users
    │
    ├── profiles
    │
    └── enterprise_memberships ── enterprises
                                      │
                                      ├── orders
                                      ├── workers
                                      ├── workshops
                                      ├── work_orders
                                      ├── production_tasks
                                      ├── tasks
                                      └── finance / shipping
```

- `auth.users` 保存登录身份、密码凭据和 Supabase Session。
- `profiles` 保存姓名、头像和业务联系方式，不保存密码。
- `enterprises` 保存企业主体信息和企业类型。
- `enterprise_memberships` 保存用户所属企业、角色、状态和默认企业。
- 一个用户可以加入多个企业，但每次请求只能在一个经过验证的活动企业上下文中执行。
- 角色和权限不能从用户可编辑的 metadata 读取；必须来自受保护的成员关系和角色表。

### 4.2 旧数据兼容

- 首先获取线上 Schema 和数据量的只读快照，并完成可恢复备份。
- 保留原 `users`、`tenants`、`tenant_users` 数据直至迁移验收完成。
- 将旧企业映射到 `enterprises`，将旧成员映射到 `enterprise_memberships`，记录稳定的映射关系。
- 旧自定义密码哈希不得伪装成 Supabase Auth 密码。已有用户通过一次性密码重置激活新身份。
- 生产环境删除内存演示账号；演示数据仅通过明确的开发 seed 创建。
- 兼容读写只存在于迁移窗口，完成验收后删除旧路径，避免永久双写。

### 4.3 迁移与 Schema 真相源

- 新建 `supabase/migrations/`，它是数据库变更唯一可执行来源。
- `src/db/schema.ts` 必须与已应用迁移一致，用于 TypeScript 类型和关系定义。
- 现有 `scripts/init-*.sql` 在迁移完成后归档为历史资料，不再直接用于建库。
- 每个迁移包含必要的表、约束、索引、Grants、RLS 和策略。
- 迁移必须先在本地或临时数据库执行，再备份并应用到线上。
- 迁移不得清空表、静默丢弃字段或覆盖现有 v2 数据。

### 4.4 RLS 与密钥边界

- `public` 暴露 Schema 中的每张业务表都启用 RLS。
- `anon` 默认无业务表写权限；公开读取必须逐项列明。
- `authenticated` 只获得实际需要的操作权限，并由 RLS 限定到活动企业和资源所有权。
- 普通页面和 API 使用用户 Session 创建的客户端，不用 Secret Key 代替权限判断。
- Secret Key 仅用于受控注册初始化、系统运维和迁移，并且只存在于服务端环境变量。
- Storage bucket 使用私有对象或受控签名 URL；上传、读取、更新和删除均有企业/用户策略。

## 5. 认证与授权

- 使用 `@supabase/ssr` 维护 Next.js 服务端与浏览器 Cookie Session。
- 删除内存中的 Session、验证码、OAuth state、密码重置令牌和用户存储。
- 登录、注册、邮箱/手机验证、密码重置和 OAuth 使用 Supabase Auth 正式流程。
- 登录、注册、验证码、重置密码和上传接口必须限流。
- 每个受保护请求依次验证：有效身份、活动企业成员关系、资源企业归属、具体权限。
- 管理员、生产、质检、财务、工人、经销商和供应商采用最小权限；普通登录用户不能自动升级为管理员。
- 页面导航权限和服务端写权限使用同一个权限定义，但服务端检查是最终权威。
- 经销商 DTO 隐藏工人、工资、成本、利润和内部备注；工人 DTO 只返回自己的任务和工资。

## 6. 业务领域与状态机

### 6.1 数据层次

```text
企业协作订单
└── 空间/模块
    └── 产品
        └── 生产工单
            └── 工序任务
                ├── 进度/状态日志
                └── 计件工资记录
```

- `orders` 表示企业之间的订单和整体交付状态。
- `work_orders` 表示产品或生产批次的排产、生产、质检和入库。
- `production_tasks` 表示分配给具体工人或工位的工序任务，并正式关联 `work_order_id`。
- `order_exchanges` 只管理企业之间的发送、接受、退回、拒绝和撤回。
- `wage_records` 只管理工序任务产生的工资及其审批、结算和支付状态。

### 6.2 核心流程

```text
经销商提交订单
→ 工厂接收或退回修改
→ 确认并进入订单池
→ 拆分生产工单
→ 分配车间和工人
→ 工人开工
→ 工人提交
→ 质检通过、返工或异常
→ 工单完成并入库
→ 订单待发货
→ 发货
→ 签收完成
```

### 6.3 状态规则

- 每个聚合仅维护自身状态，不由页面直接写入其他聚合的状态。
- 所有允许转换集中定义在领域模块，页面、API 和测试引用同一常量和转换函数。
- 每次状态变化必须记录操作者、企业、旧状态、新状态、原因和时间。
- 状态更新、审计日志、工资记录和上级汇总在同一事务中完成。
- 工人提交任务时生成暂估工资；质检通过后批准，返工或拒绝时重新计算或拒绝。
- 只有全部必需工单完成并入库后，订单才能进入待发货。
- 发货创建正式 `shipments` 记录，物流公司和运单号不得写入订单备注。
- 重复请求通过幂等键返回同一结果，不得创建重复工资、日志或发货记录。

## 7. 模块边界

1. 身份与企业组织
2. 企业协作与订单
3. 拆单、生产工单与工序任务
4. 质检、异常与返工
5. 工资规则、结算与支付
6. 入库、发货与物流
7. 内部任务与通知
8. 看板和报表

领域模块通过明确的服务接口通信，不允许页面组件直接跨多个表完成业务事务。

## 8. API 与代码结构

### 8.1 分层

每个领域采用以下边界：

```text
schema → repository → service → route/server action
```

- `schema`：Zod 输入、查询参数、状态和公开 DTO。
- `repository`：单表或明确聚合的数据访问，不包含 HTTP 逻辑。
- `service`：授权、状态转换、事务、幂等和审计日志。
- `route/server action`：解析请求、调用服务并映射为统一响应。

### 8.2 请求与响应

- 所有路径参数、查询参数和请求体必须使用 Zod 验证。
- 成功响应为 `{ data, meta? }`。
- 失败响应为 `{ error: { code, message, fieldErrors?, requestId } }`。
- HTTP 状态码统一：400 输入错误、401 未登录、403 无权限、404 不存在、409 状态冲突、422 业务校验失败、429 限流、500 未知服务端错误。
- 错误响应不得直接暴露 Supabase、SQL、密钥或堆栈信息。
- 创建和关键状态操作支持幂等键。

## 9. 界面与体验

项目面向企业内部员工，采用克制、信息密集且清晰的 B2B ERP 风格。

- 全站只保留一个应用壳和一套角色导航。
- 列表页统一为“标题/说明、主操作、筛选、统计、表格”。
- 每个页面只有一个明确主操作，例如“新建订单”“分配工人”“提交质检”。
- 编辑使用表单页或抽屉，简单确认使用对话框。
- 手机端将宽表格转换为卡片或详情抽屉，交互目标至少 44px。
- 所有页面具有加载、空数据、权限不足、请求失败和重试状态。
- 使用 Toast 和字段级错误替代 `alert()`。
- 修复全部乱码，移除硬编码质量指标、演示分类、死页面和重复入口。
- 统一颜色、间距、状态徽章、金额与日期格式，满足 WCAG AA 对比度。
- 超大组件按步骤和领域拆分；拆分不能改变已确认业务行为。

## 10. 错误、安全与可观测性

- 增加 `error.tsx`、`global-error.tsx`、`not-found.tsx`、401 和 403 页面。
- 设置 CSP、点击劫持防护、Referrer Policy、内容类型保护等安全头。
- Next Image 只允许明确列出的远程域名。
- 生产环境关闭调试和测试端点。
- 服务端输出结构化日志并生成 `requestId`，日志不得包含密码、Cookie、验证码、访问令牌或密钥。
- 已知业务错误返回稳定错误码；未知异常记录服务端详情并向用户返回通用提示。
- 对认证、权限拒绝、迁移、关键状态转换和支付状态变化保留审计证据。

## 11. 测试体系

- 单元测试覆盖状态机、金额、工资、权限和 DTO 过滤。
- 数据库集成测试覆盖迁移、约束、索引、Grants、RLS 和跨企业访问拒绝。
- API 测试覆盖认证、Zod 校验、授权、幂等、状态冲突和事务回滚。
- 组件测试覆盖关键表单、加载、空数据、错误和权限状态。
- E2E 覆盖注册登录、创建订单、接单、拆单、生产、质检返工、发货和工资结算。
- 线上 smoke test 只使用专用测试企业和账号，不修改真实业务数据。

## 12. CI、部署与发布

- 功能从 `xiangzhi2022/erpv1` 的 `codex/` 分支提交，通过 PR 进入 `main`。
- `LOVEZHI163/erpv1` 定时同步上游 `main`，Netlify 从镜像 `main` 自动部署。
- CI 门禁包含单元/集成测试、TypeScript、零 ESLint 错误与警告、生产构建和迁移检查。
- Netlify Deploy Preview 使用独立测试数据库环境，不能连接生产 Supabase。
- 生产部署使用正式 Supabase 环境变量，Secret Key 标记为服务端 Secret。
- 构建流程简化为锁定依赖安装和标准 Next.js 构建，移除 Netlify 不使用的自定义服务器打包。
- 每次数据库变更先备份、验证迁移与回滚策略，再安排生产发布。

## 13. 阶段一验收标准

阶段一“生产安全与数据底座”必须同时满足：

- 线上现有 v2 数据已备份并完成 Schema 清单。
- `supabase/migrations/` 成为唯一迁移来源，迁移可在空库和保留 v2 数据的数据库重复验证。
- Supabase Auth/SSR 登录、退出、Session 刷新和密码重置稳定运行。
- 所有受保护请求验证身份、企业成员、资源归属和权限。
- 所有业务表拥有 `enterprise_id`、必要约束、索引、Grants 和 RLS。
- `anon` 无业务写权限，跨企业访问测试全部被拒绝。
- 统一 API 错误格式、Zod 校验、限流、安全头和错误页面落地。
- 生产调试端点关闭，日志不泄漏敏感信息。
- 测试、TypeScript、零警告 Lint、生产构建和数据库安全测试全部通过。
- 现有业务代码可以继续编译，后续阶段能够在新底座上增量迁移。

## 14. 非目标

- 阶段一不重做全部页面视觉。
- 阶段一不新增超出现有 ERP 范围的 CRM、采购预测或复杂库存功能。
- 不在没有备份和迁移验证的情况下修改线上 Supabase。
- 不通过 Secret Key 绕过正常用户授权来“临时修通”业务。
- 不同时维护新旧两套永久数据写入路径。
